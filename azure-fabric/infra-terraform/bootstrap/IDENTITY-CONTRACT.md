# Bootstrap Identity, Seed and GitHub OIDC — Offline Contract

> OpenSpec \`bootstrap-fabric-infrastructure\` Task 1.2. **Only desired state, never proof of privilege.** Use \`tools/fabric_bootstrap_identity.py\` and \`tests/test_fabric_bootstrap_identity.py\`; this contract does not manage existing applications, create new applications, set repository secrets or mint tokens.

1. Seed Operator is an existing privileged HUMAN/operator with separately authorized, short-lived Tenant A and Tenant B scope. The required non-secret \`seed_operator.authorization_reference\` is a traceability label, NOT an authorization token or verified grant. The validator checks the operator's target Tenant IDs against Bootstrap Profile, without ever assuming Graph tenant-admin rights, subscription RBAC, Fabric Tenant settings or GitHub Environment permissions.
2. Applications must be exactly three mutually distinct planned \`create-new\` records: \`backend_operator\` (Tenant A), \`blob_reader\` (Tenant A) and \`fabric_deployer\` (Tenant B, same as A for A→A′). Their display names are \`hdp-<environment>-backend-operator\`, \`hdp-<environment>-blob-reader\`, \`hdp-<environment>-fabric-deployer\`. No existing \`github-terraform\` SPN is imported, adopted, overwritten or recreated by name. Before Terraform can execute, external inventory must prove all names vacant.
3. GitHub OIDC uses two DIFFERENT protected environments: \`fabric-<environment>-backend\` and \`fabric-<environment>-deployer\`. Exact repo \`JohnZhang-DataForge/healthcare-data-platform\`, issuer \`https://token.actions.githubusercontent.com\`, audience \`api://AzureADTokenExchange\`, and required source branch \`refs/heads/main\`. Subjects are \`repo:<repo>:environment:<protected environment>\`. GitHub's OIDC subject with an Environment does **NOT** also encode the branch; deployment-branch rules and required reviewers for EACH GitHub Environment must be configured and manually verified. A \`pull_request\` or feature branch must NEVER obtain cloud write tokens.
4. Blob Reader intentionally has **no** GitHub OIDC binding in this first contract: its data-access credential mechanism (Workspace Identity or Key Vault secret reference) is independent of CI/CD. Backend Operator is permitted **only** approved State container data access (not landing); Blob Reader only Landing read; Fabric Deployer only separately granted Fabric permissions. App registration itself does not imply RBAC.
5. Identifiers for newly created apps do not exist at plan time; input MUST NOT include invented Client IDs, existing SPN IDs or any credential. Once separately provisioned, \`validate_resolved_client_ids\` checks three distinct nonzero canonical Client IDs and exact Tenant provenance before non-secret downstream handoff, but still returns \`verified=false\`.
6. The output always includes \`seed_authorization_verified=false\`, \`github_environment_protection_verified=false\`, \`application_inventory_verified=false\`, \`app_client_ids_resolved=false\`, \`verified=false\`, \`cloud_executed=false\` and \`terraform_executed=false\`. Offline validity is not permission to execute.
7. Subsequent Terraform modules SHALL default-deny any new identity/permission assignments and SHALL NOT auto-import or auto-adopt existing Apps. Cross-tenant AzureAD provider instances and exact role scopes still require official Provider/IAM review (Task 2.1). The currently operating Self-Runner \`azure-infra.yaml\` is untouched.

**Identity v1 request keys (required, no extras):** \`schema_version=1\`, \`environment\`, \`seed_operator={backend_tenant_id,fabric_tenant_id,authorization_reference}\`, \`applications={backend_operator,fabric_deployer,blob_reader}\` each \`{operation,tenant_id,display_name}\`, and \`oidc_bindings={backend_operator,fabric_deployer}\` each \`{repository,environment,ref,issuer,audience,protected_environment_required}\`. The approval/environment protection fields in JSON are intended guards, never evidence of an actual configuration.

## Cross-repository and immutable GitHub OIDC subject blocker (2026-10-20)

GitHub created both project repositories after **2026-07-15**, when immutable OIDC subject prefixes with `@owner_id` and `@repository_id` became the default. The current two Entra federated credentials in `bootstrap/identity/main.tf` are still **name-only** `repo:JohnZhang-DataForge/healthcare-data-platform:environment:...`, and they address a different repository than the **Self-Runner** controller. Their `-backend`/`-deployer` Environment subjects do not equal future `bootstrap`/`plan`/`apply` protected job environments, either.

**Never enable `identity_creation_approved` based on the existing Terraform source:** first review the chosen executor-repository, immutable GitHub `sub` format, phase + role Entra credential topology, actual protected GitHub Environment reviewers/branch policies, and explicit cloud Seed authorization. The GitHub owner/repository IDs stored in static audit output are a current snapshot, **not token verification or a portability assumption**. For another repository, derive the IDs from independently verified ownership metadata and re-review the trust. This remains a code-only HOLD; no live providers or credentials have been created. Official: <https://learn.microsoft.com/en-us/entra/workload-id/workload-identities-github-immutable-subjects>.
