## Contract facts and unresolved live checks

- The latest provider released at execution time may differ. Bootstrap code SHALL stay pinned to the selected version until independent reviewed upgrade. AzureAD 3.x uses Microsoft Graph, not self-granted Graph permissions. Application federation with service-principal authentication requires application owner permissions (\`Application.ReadWrite.OwnedBy\` when owner) or a separately consented broader Graph role; consent cannot be manufactured by Terraform. [AzureAD federation IAM](https://registry.terraform.io/providers/hashicorp/azuread/3.8.0/docs/resources/application_federated_identity_credential).
- Use separate Tenant A / Tenant B AzureAD provider alias roots or explicit provider mappings. Do NOT silently collapse identity when Tenant IDs match; app registration / service principals must be separate per role. Github subject restricted to protected Environment; Branch restriction belongs in GitHub Environment configuration because OIDC Environment subject does not itself include the Git ref. No PR workflow gets \`id-token: write\`.
- \`Backend Operator\`: \`Storage Blob Data Contributor\` limited to State **container** scope, for remote Blob lease/read/write; backend key prefixes do NOT provide Azure RBAC separation. \`Blob Reader\`: \`Storage Blob Data Reader\` limited to Landing container scope. User/Group/Security Group roles are not equivalent to Fabric tenant admin, and Entra \`azuread_group\` is not itself authorization to change the Fabric tenant settings. [Microsoft Azure container-level RBAC guidance](https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access).
- Fresh new Storage requires a separate initial Bootstrap State (protected local or independently existing private Backend), never a backend residing inside the not-yet-created account. In \`reuse-existing\`, old account/container/state must not be managed, imported, rewritten or auto-adopted. No destructive default state operations.
- Azure Fabric Capacity HCL structure is \`azapi_resource\` with \`type = "Microsoft.Fabric/capacities@2023-11-01"\`, \`name\`, \`location\`, \`parent_id\` resource group ID, \`sku = {name="F...",tier="Fabric"}\`, \`body.properties.administration.members\`. ARM name regex \`^[a-z][a-z0-9]*$\`, length 3–63. Administrators are identity values, **not** automatically billable approval. Capacity starts charging upon creation (see [Fabric provider guide](https://registry.terraform.io/providers/microsoft/fabric/latest/docs/guides/fabric_capacity_setup)); therefore default-off, external budget approval and \`prevent_destroy\` MUST be independent.
- Do not implement automatic Capacity suspend/resume or creation/deletion per task. Offline \`terraform fmt -check\` parses HCL; no provider download, \`validate\`, \`init\` or \`plan\` in PR CI. Real provider schema, Owner/Graph/RBAC, SKU availability, quota, region and bills remain **HOLD** until separately approved read-only/controlled checks.

## Pinned AzureRM 4.60.0 Storage/Container/RBAC schema cross-check (code-only)

- [azurerm_storage_container v4.60.0](https://registry.terraform.io/providers/hashicorp/azurerm/4.60.0/docs/resources/storage_container): `storage_account_id` selects ARM rather than Blob Data Plane API; the `resource_manager_id` output is the ARM scope. `container_access_type=private` prevents anonymous reads.
- [azurerm_role_assignment v4.60.0](https://registry.terraform.io/providers/hashicorp/azurerm/4.60.0/docs/resources/role_assignment): `scope`, `principal_id` (SP object ID, NOT application Client ID), `principal_type=ServicePrincipal`, `role_definition_name` are documented. [Microsoft Blob RBAC scope](https://learn.microsoft.com/en-us/azure/storage/blobs/assign-azure-role-data-access) authorizes **container level** roles; State Blob key prefix is not RBAC isolation.
- [azurerm_storage_account v4.60.0](https://registry.terraform.io/providers/hashicorp/azurerm/4.60.0/docs/resources/storage_account): disables Shared Key/public anonymous access, public network, uses TLS 1.2+ and OAuth portal by default for NEW resources only. Private endpoint/allowable operator and hosted runner access are intentionally NOT implemented and are deployment blockers. Container ACL updates may still need Shared Key in some provider flows. **Terraform fmt only** is not Provider initialization/schema introspection, and no Azure runtime permissions were tested.

## Capacity Root exact ARM 2023-11-01 schema

- [Microsoft Fabric capacity 2023-11-01 official AzAPI example](https://learn.microsoft.com/en-us/azure/templates/microsoft.fabric/2023-11-01/capacities): `type`, `name`, `parent_id`, `location` and dynamic `body.properties.administration.members` plus `body.sku.name/tier=Fabric`. Version `Azure/azapi 2.8.0` is pinned as a candidate; not initialized/validated with the live Azure provider.
- Capacity RG belongs to Tenant B Subscription and is externally inventoried. It is **not necessarily the Tenant A Storage Subscription** in A→B; real Tenant/subscription ownership and ID/Resource Group vacancy must be verified. The ARM Resource ID is not assumed to be the Fabric workspace Capacity UUID.
- No auto Suspend/Resume, no task-based create/delete, no paid Actions credentials. Only HCL fmt and static tests; cost/protected Environment approval is a separate authorization prerequisite.
