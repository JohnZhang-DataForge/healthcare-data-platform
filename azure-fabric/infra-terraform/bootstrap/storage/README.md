# Fabric Bootstrap Storage / RBAC Root (code only)

Owned by OpenSpec `bootstrap-fabric-infrastructure` Task 2.3. This isolated Terraform Root does **not** execute by itself. No Azure cloud operation, Terraform init/plan/apply/destroy/import, data reads or paid resource creation are authorized.

## Ownership and two mutually exclusive modes

- Default `bootstrap_mode=reuse-existing`: **zero resources, zero data sources, zero role assignments**. The only target is a passed-in **unverified** existing `johnzhang` Azure Storage ARM ID; no import, automatic adoption, state migration or permission mutation. Legacy `landing`, `tfstate`, `dev/*.tfstate`, and the historical `healthcare-omop` Workspace are never managed by this Root.
- `bootstrap_mode=fresh-bootstrap`: candidates are a NEW `rg-hdp-<environment>` Resource Group, NEW `hdp...` globally unique Storage Account, private `landing` and `tfstate` containers. Variables do not infer mode based on missing inventory. Fresh Storage creation is default-deny and requires **independent** explicit flags for Seed, name inventory, initial State custody, approved new resource creation and private connectivity readiness. Flags are declarative assertions, **not** externally verified approvals. Even all true would still require manual authorization for Terraform operations.
- `azurerm` is pinned to 4.60.0; subscription and Tenant A are separate non-secret UUID inputs. Initial `backend "local" {}` **never points to not-yet-created Storage**. Local State is sensitive: operator must provide independently protected, backed-up and recoverable custody before a live session. No automatic `init -migrate-state`, `import` or `state mv`.
- Default-nonpublic account: public network disabled, public blob access disabled, OAuth preferred, shared key disabled. This means a private network path for backend/Reader/authorized operators has **not** yet been designed or verified. Therefore live connectivity must remain HOLD, including hosted runners without private access. Because Storage Containers use `storage_account_id` they use the ARM API; modifications to container ACL with Shared Key disabled must be separately reviewed.
- `rbac_creation_approved=false` by default, independently requiring identity provenance (SERVICE PRINCIPAL **object IDs**, not application client IDs), distinct Backend Operator and Reader IDs, fresh-only resources, and upstream Storage gate. Role assignments attach **only** to newly declared container `resource_manager_id`: State gets `Storage Blob Data Contributor` for Backend Operator; Landing gets `Storage Blob Data Reader` for Blob Reader. No account/RG/subscription-scope grant, no Landing writer, no Fabric Deployer write access.
- All managed resources have `prevent_destroy`. This does not prove ownership, preserve a State whose block is removed, or prevent billing. Documented inventories, state backup/lock, immutable approvals and separate execution gates remain mandatory.

## Inputs, offline verification and follow-up

All required inputs are non-secret and must conform to [Bootstrap Profile](../PROFILE-CONTRACT.md) and [Identity/OIDC](../IDENTITY-CONTRACT.md). The Root is not yet automatically wired to those Python validations. Zero-safe outputs are unverified IDs/names, State prefix and exact container scopes; no keys/SAS/token or credentials. Pending cross-change handoff 3.1 must verify ID provenance and real State vacancy.

Only GitHub-hosted `terraform fmt -check` and static Python tests are allowed in PR CI. The former checks formatting, **not provider schema**. Read the [Provider references](../PROVIDER-SCHEMA-REFERENCE.md). Work on `bootstrap/capacity/` is a separate Task 2.4. Do not alter the prior seven Roots or Self-Runner `azure-infra.yaml`.
